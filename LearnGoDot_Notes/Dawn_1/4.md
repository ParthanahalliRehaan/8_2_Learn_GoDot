# Why _ready()?
**That analogy is useful, but only approximately.** `_ready()` is closer to an initialization lifecycle hook than to `server.js` itself.

## `_ready()` in one line

> **`_ready()` is a Godot lifecycle function that runs when a node has entered the scene tree and is ready to initialize itself.**

Think:

```text
Godot starts
   ↓
Scene loaded
   ↓
Nodes created
   ↓
Node enters scene tree
   ↓
_ready()
   ↓
Initialization
```

## Backend analogy

In a backend:

```text
server.js
   ↓
application starts
   ↓
initialize dependencies
   ↓
start server
```

In Godot:

```text
Main.tscn
   ↓
Godot loads scene
   ↓
creates nodes
   ↓
_ready()
   ↓
initialize node
```

So `_ready()` is **not exactly `server.js`**.

A better comparison is:

| Godot                | Backend analogy                     |
| -------------------- | ----------------------------------- |
| `.tscn`              | Application/module structure        |
| `.gd`                | Application/module logic            |
| `_ready()`           | Initialization/startup hook         |
| `_process()`         | Repeated runtime/event loop work    |
| `_physics_process()` | Fixed-rate physics/update loop      |
| Node                 | Component/object                    |
| Scene                | Reusable component/module structure |

For example, a `Player.gd` might conceptually have:

```text
Player.gd
│
├── _ready()
│     └── initialize player
│
├── _process()
│     └── per-frame logic
│
└── _physics_process()
      └── movement/physics logic
```

## 📝 Dawn 1 note

> **`_ready()`** → Godot lifecycle function called when a node is ready in the scene tree. Commonly used for initialization/setup. Usually runs once per node instance.

And the important mental model:

```text
.tscn → WHAT exists
.gd   → WHAT it does
_ready() → WHEN initialization happens
```

That last three-line model is worth keeping for the final notes.
